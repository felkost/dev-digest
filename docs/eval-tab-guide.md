# Вкладка Evals — інструкція для початківця

> Де знайти: **агент → вкладка «Evals»** (Skills Lab → Agents → обери агента → Evals).
> Окремого «EvalDashboard» немає **навмисно** — evals прив'язані до конкретного агента
> (у кожного свій prompt / skills / модель, тож і своя регресійна база), тому живуть усередині агента.

---

## 1. Що це і навіщо

Уяви **юніт-тести, але для AI-рев'ювера**. Ти постійно змінюєш агента: правиш prompt, додаєш
skills, перемикаєш модель. Головне питання — **стало краще чи гірше?** Без evals це вгадування.
Evals дають **числа**.

**Eval case** = зафіксований шматок коду (diff) + очікування «що хороший рев'ювер тут має зробити».
Ти проганяєш агента по всіх кейсах і бачиш, скільки він вгадав.

---

## 2. Два типи очікувань (основа всього)

| Тип | Що означає | Коли «провал» | Наслідок |
|-----|-----------|---------------|----------|
| **must_find** | Тут є **реальна проблема** — агент **мусить** позначити її на цих рядках | агент **не знайшов** | падає **Recall** |
| **must_not_flag** | Це **безпечний код** (guard, рефакторинг) — агент **не має** сюди чіпатися | агент **помилково позначив** | падає **Precision** |

Демо-кейси (сідовані) — це якраз ілюстрація кожного випадку:

| Кейс | Тип | Що перевіряє |
|------|-----|--------------|
| missing await drops usage report | must_find | чи ловить пропущений `await` |
| N+1 query in notification fan-out | must_find | чи ловить N+1 запит у циклі |
| safe guard clause addition | must_not_flag | чи **не** чіпає доданий безпечний guard |
| SQL string concat plus safe rename | must_find **+** must_not_flag | має зловити SQL-конкатенацію і **не** чіпати безпечний rename |
| clean diff — comment-only change | 0 очікувань | косметичний diff → агент має **промовчати** (будь-яке зауваження = мінус precision) |

---

## 3. Три метрики (причина → наслідок)

| Метрика | Простими словами | Чому падає | Що це означає |
|---------|------------------|-----------|---------------|
| **Recall** | З усіх реальних багів — скільки агент зловив | пропустив `must_find` | Агент **сліпий** до частини багів → у проді пропускатиме |
| **Precision** | З усього, що агент позначив — скільки по ділу | позначив `must_not_flag`-зону | Агент **шумить** (false positives) → люди перестають довіряти |
| **Citation accuracy** | Скільки знахідок «вижили» після grounding-перевірки (реально цитують код), а не вигадані | агент **галюцинує** — посилається на неіснуючий код | Низька = агент вигадує проблеми |
| **Cost** | $ за прогін батча | — | Скільки коштує один прогін усіх кейсів |

> Нюанс: у кейсі без `must_find` (як clean-diff) Recall завжди «зелений» (нема чого ловити) —
> там важлива лише Precision.

---

## 4. Сценарії користування

### A — перший прогін (головний)
1. Тиснеш **▶ Run all evals** → створюється **batch** (пакет).
2. Кожен кейс проганяється через агента (це **реальний виклик LLM**, коштує $).
3. У **BATCH HISTORY** з'являється рядок із recall / precision / citation / cost.
4. Клік по рядку → **drill-down**: по кожному кейсу expected vs matched (що мав знайти vs що знайшов).

### B — перетворити реальну помилку на тест
- Коли агент на справжньому PR щось **пропустив** або **зафолсив**, на картці finding є кнопка
  **«Add to evals»** — вона робить снапшот того diff у новий eval-кейс.
- Сенс: один клік — і разовий факап став **постійним регресійним тестом**, який ловитиме цю ж
  помилку в майбутньому.

### C — редагувати кейс
- Олівець біля кейсу → правиш diff / очікування (тип, файл, рядки start/end).
- Номери рядків — за **new-side** нумерацією diff (рядки видалення `-` не рахуються).

### D — порівняти зміни агента в часі (найцінніше)
1. Прогнав батч на поточному prompt.
2. Пішов у **Config**, покращив prompt / додав skill.
3. Знову **Run all evals**.
4. У **TREND** видно лінію: піднявся recall чи впав. Можна вибрати **два full-батчі** й побачити точну дельту.
5. Кожен батч зберігає **agent snapshot / fingerprint** (prompt + skills + модель) — тому видно
   «цей результат був на конфізі A, той — на B».

### E — calibration batch (швидка перевірка)
- Можна прогнати **не всі**, а підмножину кейсів — це «calibration» батч.
- Він **не** лягає на TREND (це разова точкова перевірка, а не повна регресія) і не бере участі
  в KPI-порівняннях.

---

## 5. Рекомендований перший підхід

1. Відкрий агента → **Evals**.
2. **Один раз** тисни **Run all evals**, дочекайся результату.
3. Подивись recall/precision у BATCH HISTORY; зроби drill-down на кейс, що не пройшов.
4. Зміни щось у **Config** агента → знову Run all → порівняй два батчі в TREND.
5. Далі — лови реальні факапи на PR кнопкою «Add to evals» й нарощуй свою регресійну базу.

---

## 6. Передумови (щоб вкладка працювала)

- **Міграції застосовані:** `cd server && pnpm db:migrate` (сервер не мігрує сам).
- **Дані засідані:** `cd server && pnpm db:seed`.
  > Сід кейсів іде через детерміновані UUID + `onConflictDoNothing` — тобто повторний seed
  > **не перезаписує** вже наявні кейси. Якщо змінив seed-дані, спершу видали старі рядки
  > (`delete from eval_runs; delete from eval_batches; delete from eval_cases`), тоді пересідь.
- **API перезапущений після появи eval-модуля:** Fastify реєструє роути при старті, тож процес,
  запущений до появи модуля, не матиме `/agents/:id/evals/*` — потрібен рестарт `pnpm dev`.
